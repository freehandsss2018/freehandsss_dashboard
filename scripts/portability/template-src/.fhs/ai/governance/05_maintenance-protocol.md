# 05 — 治理維護協議

> Version: 0.1.0。治理規則要穩定、可追溯，避免兩個工作階段讀到互相衝突的版本。

## 權限與提案

純事實修正、失效連結修復及依既定格式追加例子，可在保留備份和 read-back 後進行。修改根目錄政策、既有門檻、權限、驗收準則或刪除規則，要先向專案負責人提出「現行條文、建議條文、動機、影響面」，取得明確決定後執行。新治理編號檔要先檢查是否與現有職責重疊。

## 教訓落點

可跨專案重用的調度與驗證教訓寫入 [02_model-dispatch.md](02_model-dispatch.md) 或 [03_judgment-rubrics.md](03_judgment-rubrics.md)。命令的操作陷阱寫在該命令。專案領域知識寫入專案記憶；一次性事故放在帶索引的案例庫。不要把敏感資料放入通用模板。

## 修改步驟

1. 定位唯一規則來源，讀相關窗口和已記錄的決策。
2. 修改既有治理檔前建立可辨認版本的備份；新增副本不需要備份不存在的原檔。
3. 明確標記版本；修改索引、路由及相關引用。
4. 由獨立讀者核對不變量、連結和互相矛盾之處。
5. 在交接中記下變更原因與驗證證據。

## 輪轉與健檢

handoff 變長時，先備份，保留便攜塊、當前工作及近期條目，把舊記錄歸檔並留下指標。治理文件膨脹時先提出精簡方案，避免默默刪除規則。定期核對路由路徑、版本、重複教訓、失效引用和獨立驗收的執行率。同型 workaround 一再增加，應提出根因修正。

範本只提供流程。專案負責人、備份位置、輪轉上限和健檢週期，應在根目錄 `AGENTS.md` 或專案設定中明訂。
